# 决策记录

只记影响方向的取舍：做了什么选择、为什么、替代了什么。日常实现细节住在代码与 `CHANGELOG.md`，不在这里。

---

## D-001 定位是「会话通知器」，不是账号通知器

**2026-11-17，2026-11-19 补齐。** 插件不替人看 GitHub 账号上的消息，它盯的是「这个会话在 GitHub 上做的事有没有回音」。搜索接口按 `author:@me`、`review-requested:@me`、`author:@me`+`type:issue`、`assignee:@me`、`mentions:@me` 取条目，所以任何仓库里的动作都会回到发起它的会话。

补齐的是「我开的 issue」：2.23.0 及以前只搜 `assignee:@me`，而自己开的 issue 通常没派给自己，于是维护者在里面的回复一条都到不了——实测漏了 `polang233/dsh-plugin-index#527` 的一条复核意见整整一天。同一个改动里，首次见到的仓库不再是纯基线：一天内的变化仍算新闻，否则补上的搜索会把新仓库里等着的回复当成历史吞掉。

替代的是早期「把某个仓库的新事件播报给订阅了它的会话」——那个模型需要用户先想清楚「订阅」，而且让插件与账号消息箱纠缠在一起。平台事实是：App 令牌没有收件箱（`/notifications` 返回 403），用户令牌的通知只说明「为什么通知你」，给不出「这是哪个会话的事」。身份只能由工作区提供，所以归属必须自己算。

## D-002 归属分两层：仓库级给接管者，条目级给干活的那个会话

**2026-11-17。** 仓库级事实（默认分支 CI、安全告警、定时任务）只给接管了这个仓库的会话；条目级事实（某个 PR / issue 上的评审、指派、@）先给工作区就在这个仓库的会话，其次接管者；两者都没有时不给任何人（见 D-014）。

替代的是「所有会话拿同一份流」：那会让两个 agent 同时以为同一件事归自己，而插件不该仲裁谁先动手。

## D-003 「接管」取代「订阅」

**2026-11-17。** 一个会话接管一个仓库，意味着它承担这个仓库的整仓信号与归档；术语从「订阅仓库」改成「接管仓库」，「取消订阅」改成「释放」。

替代的是订阅语义：订阅听起来是「追踪事件」，而实际行为是「对这个仓库负责」。同一个工作区里，第一个出现的会话自动接管它所在的仓库，后来的会话默认没有接管——不需要用户配置。

## D-004 清理分档，且不再是开关

**2026-11-18。** 条目级线程只标已读（谁收到谁做，幂等）；仓库级线程才进 Done（只有接管者有资格替这个仓库做账）。面板上不再有「关闭 / 已读 / 归档」三档：这是固定行为，不是偏好。

替代的是可切换的清理档位——两个开关叠在一起，用户既不知道当前生效哪个，也不知道归档范围是谁的仓库。

## D-005 每个来源的安全告警聚合成一条

**2026-11-18。** 一个仓库开着二十条 Dependabot 告警时，只发一条「20 open advisories (6 high, 8 medium, 6 low): node-forge, minimatch」。

替代的是「一条告警一个事件」：实测一次轮询注入了 20 条通知，一次升级会变成二十条噪音。

## D-006 醒不醒是额外动作，门没过就退回被动注入

**2026-11-18。** 主动唤醒的五道门（模式、角色、归属、空闲、预算）任一不过，事实仍在下一轮随注入到达；只有全过才额外开一轮。

替代的是「等空闲窗，等到就注入，等不到就一直等」：实测一条事实在一个长回合里被按住了近三小时。

## D-007 归属按全体会话计算，空闲只决定投递时机

**2026-11-18。** 一条属于我仓库的事实，即使我正在跑回合也归我，它等我，而不是交给恰好空闲的别的会话。

替代的是「按当前可投递的会话算归属」：实测它把一条本仓库的 issue 叫醒了一个别的仓库的会话。

## D-008 不做角色系统（维护者 / 协作者）

**2026-11-18。** 维护者就是「接管了这个仓库的会话」，协作者是「在这个仓库的某个条目上干活」——角色由行为自然产生，不额外引入身份、勾选或分支门槛。

替代的是「用分支名推断协作者身份」：那会把「在分支上工作」变成使用插件的前提，是一种工程上的额外要求。

## D-009 路由准入交给宿主，不再自己看请求头

**2026-11-18，2026-11-19 收紧。** 每条 HTTP 路由先调 `ctx.connection.requestRejection(request)`（`inject` 声明 `connection`）：401 表示没有凭据、403 表示来源不可信，`undefined` 才继续；写设置另要每进程 token。宿主没有这个服务、或它抛错时，直接 403。

替代的是自家写的 `Sec-Fetch-Site`/`Origin` 规则：市场维护者指出它绕过了 DSH 的访问检查，而桌面壳的 fetch 走 IPC 桥、没有 `Sec-Fetch-Site`，自家规则既漏又误伤（2.21.2 曾因此让胶囊消失）。2.21.4 还留着「旧宿主没有该服务时看请求头」的兜底，维护者复核后（#527）指出认证服务缺失或异常时仍可被伪造的请求头绕过；2.23.x 起两条路都封死。代价是明说：在没有 `connection` 服务的旧宿主上，面板的路由一律 403，只有状态与投递照常——插件把面板交给一个自己无法验证调用者的环境，不划算。

## D-010 通知文本只写事实

**2026-11-18。** 注入的每条通知只有一行事实与一句「它在问你要什么」（`[请你评审]`、`[CI 失败]`、`[你的 PR 有冲突]`…），抬头说明这是后台派发；不写读取身份、收口命令、重提窗口、唤醒预算、轮询节奏。

替代的是「把插件的机制一起写进 agent 的上下文」：那是占上下文、对判断无用的噪音。收口命令仍可通过 `list` 与 `docs/configuration.md` 找到。

## D-011 轮询跟随回合，空闲只读一次心跳

**2026-11-18。** 回合开始一次、进行中按 `intervalMs`、结束一次；`quiet` 模式空闲完全不访问 GitHub，`wakeup` 模式空闲也按同一间隔读一次，否则「你不在时叫醒你」不可能发生。

替代的是固定间隔的常驻轮询：既费请求，也让「插件到底在不在跑」无法解释。

## D-012 待投事实不过期，回读后按 48 小时丢弃

**2026-11-18。** 一条已经取到、但没送到任何会话的事实不会因为时间而消失；它会在下次投递时随注入到达。唯一的上限是 48 小时后丢弃并在 `notes` 里说明。

替代的是「按 6 小时重提窗口判断」：issue 与评论只报一次，误判过期等于永久丢失。

## D-013 发布是用户的取舍，不是工程的收尾

**2026-11-18。** 改版本、写发布条目、推 main、发 npm、发版前后的一切对外动作都要先拿到明确同意；同一件事的多轮修改攒成一次发布。

替代的是「修完就发一版」：单轮实现的健康度不够格充当对外承诺，而把用户当回归测试的代价比等待更高。

## D-014 没人认领的仓库，条目只入队不上人

**2026-11-19。** 条目级事实所在的仓库里既没有会话在工作、也没有会话接管它时，这条事实不进任何会话：留在队列与面板里，日志写清原因；要看这类回音，就把那个仓库加成接管仓库。

替代的是「给最近说话的那个会话」：实测 `polang233/dsh-plugin-index#527` 的回音唤醒了 `noema·e808`——一个和这个仓库毫无关系的会话。它既开了回合又答非所问，代价比没人提醒更高。

## D-015 铃铛里没读的线程不等于今天的新闻

**2026-11-19。** 通知流只报「上一轮之后有变动」的线程；第一次拉取没有上一轮，就只信一天以内的变动。GitHub 的 reason `author`（你自己创建了这个线程）整条丢掉。

替代的是「没读过的通知都是新闻」：装好插件的那一刻，`Noema-Harness/noema-agent` 铃铛里积了四天、10 条自己创建的 issue 全倒进接管它的会话。那些 issue 在装插件之前就存在，是我自己开的，既不是回音也不是待办。代价是：铃铛里躺了超过一天、又来不及在上一轮之后被看到的线程不会触发提醒——它们仍在队列与面板里，只是不喊人。

## D-016 别人开进我仓库的 PR 与 issue 也算我的事

**2026-11-19。** 角色判定的第三处来源：如果仓库对我是 owner 或 admin，别人开进来的 PR 与 issue 就是 `incoming`，不管有没有指派我、有没有 @我。判据来自 GitHub 自己（`gh api repos/<repo> --jq .permissions.admin` 与 `.owner.login`），进程内按仓库缓存一次。

替代的是 2.1.0 起的纯身份口径：`e0e8c4c feat: route events by identity and role` 加进 `extractPrEvents` 的 `if (role === null) continue;` 把「watched 仓库里的 open PR」全部过滤掉了，`prRole` 只认 author / reviewer / assignee。代价在 2026-11-19 显形：`c3115644151/dsh-inbox-bridge#10`（`polang233` 修的 tarball 缺 `scripts/key.mjs`，是全量安装即崩的 P0）在仓库里躺了 16 小时，通知器一声没响。维护者的信息范围就是这个仓库里出现的东西，不是「别人对我做了动作」。

两处刻意的克制：

- **只按仓库归属判定，不按「谁在轮询它」**：`awesome-dsh-plugin/awesome-dsh-plugin`、`polang233/dsh-plugin-index` 这些 `admin=false` 的仓库里堆着别人的几百个 PR，按轮询范围算会把它们全变成待办。
- **仍然是条目级投递，不是仓库级**：仓库级只给接管者，而维护者未必接管了自己的仓库（「接管」是会话行为，见 D-008）。条目级链路——认领 → 在此干活的 → 接管者 → 否则留队列——才真能送到人手里。`incoming` 的 key 里只有「等你定」这一个状态，检查变红不追加第二条：一次提出只需要一个决定。

首次轮询沿用 D-015 的时间窗：新仓库里一天以前的 issue 当历史，免得装上的那一刻倒出历年积压。PR 不看时间窗——open PR 本身就是待办。
