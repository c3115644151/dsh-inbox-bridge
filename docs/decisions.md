# 决策记录

只记影响方向的取舍：做了什么选择、为什么、替代了什么。日常实现细节住在代码与 `CHANGELOG.md`，不在这里。

---

## D-001 定位是「会话通知器」，不是账号通知器

**2026-11-17，2026-11-19 补齐。** 插件不替人看 GitHub 账号上的消息，它盯的是「这个会话在 GitHub 上做的事有没有回音」。搜索接口按 `author:@me`、`review-requested:@me`、`author:@me`+`type:issue`、`assignee:@me`、`mentions:@me` 取条目，所以任何仓库里的动作都会回到发起它的会话。

补齐的是「我开的 issue」：2.23.0 及以前只搜 `assignee:@me`，而自己开的 issue 通常没派给自己，于是维护者在里面的回复一条都到不了——实测漏了 `polang233/dsh-plugin-index#527` 的一条复核意见整整一天。同一个改动里，首次见到的仓库不再是纯基线：一天内的变化仍算新闻，否则补上的搜索会把新仓库里等着的回复当成历史吞掉。

替代的是早期「把某个仓库的新事件播报给订阅了它的会话」——那个模型需要用户先想清楚「订阅」，而且让插件与账号消息箱纠缠在一起。平台事实是：App 令牌没有收件箱（`/notifications` 返回 403），用户令牌的通知只说明「为什么通知你」，给不出「这是哪个会话的事」。身份只能由工作区提供，所以归属必须自己算。

## D-002 归属分两层：仓库级给接管者，条目级给干活的那个会话

**2026-11-17。** 仓库级事实（默认分支 CI、安全告警、定时任务）只给接管了这个仓库的会话；条目级事实（某个 PR / issue 上的评审、指派、@）先给工作区就在这个仓库的会话，其次接管者；两者都没有时不给任何人（见 D-014）。

替代的是「所有会话拿同一份流」：那会让两个 agent 同时以为同一件事归自己，而插件不该仲裁谁先动手。

## D-003 「接管」取代「订阅」

**2026-11-17。** 一个会话接管一个仓库，意味着它承担这个仓库的整仓信号与归档；术语从「订阅仓库」改成「接管仓库」，「取消订阅」改成「释放」。

替代的是订阅语义：订阅听起来是「追踪事件」，而实际行为是「对这个仓库负责」。同一个工作区里，第一个出现的会话自动接管它所在的仓库，后来的会话默认没有接管——不需要用户配置。

## D-004 清理分档，且不再是开关

**2026-11-18。** 条目级线程只标已读（谁收到谁做，幂等）；仓库级线程才进 Done（只有接管者有资格替这个仓库做账）。面板上不再有「关闭 / 已读 / 归档」三档：这是固定行为，不是偏好。

替代的是可切换的清理档位——两个开关叠在一起，用户既不知道当前生效哪个，也不知道归档范围是谁的仓库。

## D-005 每个来源的安全告警聚合成一条

**2026-11-18。** 一个仓库开着二十条 Dependabot 告警时，只发一条「20 open advisories (6 high, 8 medium, 6 low): node-forge, minimatch」。

替代的是「一条告警一个事件」：实测一次轮询注入了 20 条通知，一次升级会变成二十条噪音。

## D-006 醒不醒是额外动作，门没过就退回被动注入

**2026-11-18。** 主动唤醒的五道门（模式、角色、归属、空闲、预算）任一不过，事实仍在下一轮随注入到达；只有全过才额外开一轮。

替代的是「等空闲窗，等到就注入，等不到就一直等」：实测一条事实在一个长回合里被按住了近三小时。

## D-007 归属按全体会话计算，空闲只决定投递时机

**2026-11-18。** 一条属于我仓库的事实，即使我正在跑回合也归我，它等我，而不是交给恰好空闲的别的会话。

替代的是「按当前可投递的会话算归属」：实测它把一条本仓库的 issue 叫醒了一个别的仓库的会话。

## D-008 不做角色系统（维护者 / 协作者）

**2026-11-18。** 维护者就是「接管了这个仓库的会话」，协作者是「在这个仓库的某个条目上干活」——角色由行为自然产生，不额外引入身份、勾选或分支门槛。

替代的是「用分支名推断协作者身份」：那会把「在分支上工作」变成使用插件的前提，是一种工程上的额外要求。

## D-009 路由准入交给宿主，不再自己看请求头

**2026-11-18，2026-11-19 收紧。** 每条 HTTP 路由先调 `ctx.connection.requestRejection(request)`（`inject` 声明 `connection`）：401 表示没有凭据、403 表示来源不可信，`undefined` 才继续；写设置另要每进程 token。宿主没有这个服务、或它抛错时，直接 403。

替代的是自家写的 `Sec-Fetch-Site`/`Origin` 规则：市场维护者指出它绕过了 DSH 的访问检查，而桌面壳的 fetch 走 IPC 桥、没有 `Sec-Fetch-Site`，自家规则既漏又误伤（2.21.2 曾因此让胶囊消失）。2.21.4 还留着「旧宿主没有该服务时看请求头」的兜底，维护者复核后（#527）指出认证服务缺失或异常时仍可被伪造的请求头绕过；2.23.x 起两条路都封死。代价是明说：在没有 `connection` 服务的旧宿主上，面板的路由一律 403，只有状态与投递照常——插件把面板交给一个自己无法验证调用者的环境，不划算。

## D-010 通知文本只写事实

**2026-11-18。** 注入的每条通知只有一行事实与一句「它在问你要什么」（`[请你评审]`、`[CI 失败]`、`[你的 PR 有冲突]`…），抬头说明这是后台派发；不写读取身份、收口命令、重提窗口、唤醒预算、轮询节奏。

替代的是「把插件的机制一起写进 agent 的上下文」：那是占上下文、对判断无用的噪音。收口命令仍可通过 `list` 与 `docs/configuration.md` 找到。

## D-011 轮询跟随回合，空闲只读一次心跳

**2026-11-18。** 回合开始一次、进行中按 `intervalMs`、结束一次；`quiet` 模式空闲完全不访问 GitHub，`wakeup` 模式空闲也按同一间隔读一次，否则「你不在时叫醒你」不可能发生。

替代的是固定间隔的常驻轮询：既费请求，也让「插件到底在不在跑」无法解释。

## D-012 待投事实不过期，回读后按 48 小时丢弃

**2026-11-18。** 一条已经取到、但没送到任何会话的事实不会因为时间而消失；它会在下次投递时随注入到达。唯一的上限是 48 小时后丢弃并在 `notes` 里说明。

替代的是「按 6 小时重提窗口判断」：issue 与评论只报一次，误判过期等于永久丢失。

## D-013 发布是用户的取舍，不是工程的收尾

**2026-11-18。** 改版本、写发布条目、推 main、发 npm、发版前后的一切对外动作都要先拿到明确同意；同一件事的多轮修改攒成一次发布。

替代的是「修完就发一版」：单轮实现的健康度不够格充当对外承诺，而把用户当回归测试的代价比等待更高。

## D-014 没人认领的仓库，条目只入队不上人

**2026-11-19。** 条目级事实所在的仓库里既没有会话在工作、也没有会话接管它时，这条事实不进任何会话：留在队列与面板里，日志写清原因；要看这类回音，就把那个仓库加成接管仓库。

替代的是「给最近说话的那个会话」：实测 `polang233/dsh-plugin-index#527` 的回音唤醒了 `noema·e808`——一个和这个仓库毫无关系的会话。它既开了回合又答非所问，代价比没人提醒更高。

## D-015 铃铛里没读的线程不等于今天的新闻

**2026-11-19。** 通知流只报「上一轮之后有变动」的线程；第一次拉取没有上一轮，就只信一天以内的变动。GitHub 的 reason `author`（你自己创建了这个线程）整条丢掉。

替代的是「没读过的通知都是新闻」：装好插件的那一刻，`Noema-Harness/noema-agent` 铃铛里积了四天、10 条自己创建的 issue 全倒进接管它的会话。那些 issue 在装插件之前就存在，是我自己开的，既不是回音也不是待办。代价是：铃铛里躺了超过一天、又来不及在上一轮之后被看到的线程不会触发提醒——它们仍在队列与面板里，只是不喊人。

## D-016 别人开进我仓库的 PR 与 issue 也算我的事

**2026-11-19。** 角色判定的第三处来源：如果仓库对我是 owner 或 admin，别人开进来的 PR 与 issue 就是 `incoming`，不管有没有指派我、有没有 @我。判据来自 GitHub 自己（`gh api repos/<repo> --jq .permissions.admin` 与 `.owner.login`），进程内按仓库缓存一次。

替代的是 2.1.0 起的纯身份口径：`e0e8c4c feat: route events by identity and role` 加进 `extractPrEvents` 的 `if (role === null) continue;` 把「watched 仓库里的 open PR」全部过滤掉了，`prRole` 只认 author / reviewer / assignee。代价在 2026-11-19 显形：`c3115644151/dsh-inbox-bridge#10`（`polang233` 修的 tarball 缺 `scripts/key.mjs`，是全量安装即崩的 P0）在仓库里躺了 16 小时，通知器一声没响。维护者的信息范围就是这个仓库里出现的东西，不是「别人对我做了动作」。

两处刻意的克制：

- **只按仓库归属判定，不按「谁在轮询它」**：`awesome-dsh-plugin/awesome-dsh-plugin`、`polang233/dsh-plugin-index` 这些 `admin=false` 的仓库里堆着别人的几百个 PR，按轮询范围算会把它们全变成待办。
- **仍然是条目级投递，不是仓库级**：仓库级只给接管者，而维护者未必接管了自己的仓库（「接管」是会话行为，见 D-008）。条目级链路——认领 → 在此干活的 → 接管者 → 否则留队列——才真能送到人手里。`incoming` 的 key 里只有「等你定」这一个状态，检查变红不追加第二条：一次提出只需要一个决定。

首次轮询沿用 D-015 的时间窗：新仓库里一天以前的 issue 当历史，免得装上的那一刻倒出历年积压。PR 不看时间窗——open PR 本身就是待办。
## D-017 完成定义必须可执行，不能靠发布那一刻的自觉

**2026-11-20。** 发布合同从「人点头」改成「四条能跑的检查」：
npm test、
npm run docs:check、
npm run verify:install（打包 → 空目录安装 → 按包名 import → 跑一次 CLI），加上 CHANGELOG 里「观察到的症状 → 改了什么 → 证据」。scripts/release.mjs 在版本号写进 package.json 之后、提交之前跑安装验证，所以坏包不会留下提交，也到不了 registry。CI 另有一条同样的 job。

替代的是 2.21.4–2.23.6 那套「用户点头才发版」：它假设点头的人看得见我改动的影响面，而我给出的证据从来只证明「我改的那处有效」。11-15 到 11-20 五天里发出了 83 个版本，11-17 一天 65 个；2.22.0–2.23.2 的 tarball 缺 scripts/key.mjs，测试、文档、CI、registry 全绿，因为四道门里没有一道拆开过包。同一时期用户报的四处漏（自己开的 issue 的回复、铃铛旧线程、回音落错会话、外来 PR 无人管）都由用户发现，没有一处是项目自己发现的。

两处刻意的克制：

- **不把节奏写死成数字**。真正的病是「发了没验」，不是「发得太快」；一天一个版本若每次都能装上、每处承诺都有测试，不算失控。所以规则是「一批一发」与「同一行为一周内第二次修先补测试」，而不是冷却期。
- **保留一个逃生阀但要留痕**：--skip-verify 只用于验证流水线自身，日志写明「do not publish this build」；它不是省时间的快路。

另一个可执行的约束：任何用户可见的承诺都要在 `docs/how-it-works.md` 的「承诺与验证」表里有一行，指向一条具体的测试或命令。表外的承诺不算承诺——此前它们只写在文档里，没有测试替它站岗，于是每一次都等用户来当回归测试。

## D-018 猜不出归属就不猜（废止「唯一自己干活的会话」兜底）

**2026-11-21** 引入、「2026-11-25」废止。「我在别人仓库里开的 issue」这类条目（`role: author`、`eventTier: item`）没有可判的信号：插件看不见是哪个会话去跑了 `gh`，能用的只有「谁在那个仓库工作」「谁接管了那个仓库」「谁手动认领」——三者都为空时，D-014 让它只入队。

11-21 曾加过一条兜底：当全部会话里**恰好有一个**是 `act`（直接处理）模式时，把这类无人认领的条目交给它。11-25 实测这条兜底把 `c3115644151/chronicle-framework-agent#134` 塞进了毫不相关的 `session-d179ace2`，根因是拿「会话数恰好为一」当归属判据本身就是猜——而 `?? "act"` 让几乎所有会话都算「自己干活」，兜底极易命中错误的那个。**现已删除该兜底**：没有认领、没人工作、没人接管，就谁也不给，事实留在队列与面板里，等面板「认领」按钮或某会话接管那个仓库。

替代的选项与它们为什么不够：

- **任何会话都收（D-002 的「最后说话的人」）**：它把 #527 塞进了 noema 会话，一个和这个仓库毫无关系的回合。二选一若没有判据就是猜。
- **「唯一 `act` 会话」兜底（本条原方案，已废止）**：同上，拿会话数当判据仍是在猜，且「恰好一个」的条件在真实装机里频繁成立，错投反复出现。宁可晚到一次，也不再错送一次。
- **按「谁跑过 `gh`」判定**：宿主不记录 agent 的进程谱系，插件也拿不到。假装能判就是给下一次错投埋一个更隐蔽的理由。
- **自动接管那个仓库**：接管是仓库级的信号与归档开关（D-008、D-014），用它表达「这条回音给我」会顺手改动轮询与清理范围——一次认领变成一次配置变更。

代价写在明处：这类条目现在一定等一次显式「认领」或仓库接管才会投递，再不会自动送到一个推测的会话；这是有意的。相邻的诚实仍保留：面板按 `owner/name#kind:number` 去重（一条条目一行，计数不虚高），会话尚未绑定时不铺别人的待办、只给「另有 N 条」。

## D-019 profile 的 wakeOn 优先于覆盖层的遗留值

**2026-11-25。** profile（`cordis.patch.yml`）已配 `wakeOn: [author, reviewer, assignee]`，但 `prefs.json` 里留着一份陈旧的 `["reviewer"]`（早先切换 delivery 时 `preferenceNext` 硬塞的默认），加载时 `mergeConfig({...baseConfig, ...prefs})` 让覆盖层盖掉了 profile，于是 author 类事件既不唤醒、又因 stray 兜底误投。面板没有 wakeOn 控件，`preferenceNext` 也不处理它，用户无从在 UI 里修正。

判据：`overlayPreferences(base, prefs)` 让 base 的非空 `wakeOn` 胜过 prefs 的值；base 沉默时才保留覆盖层（保证刚切到 wakeup 的新装机仍能唤醒某人，而不是 `no-role`）。两个加载点（启动时 `Object.assign(options, …)` 与 `applyPrefs` 写回）都走这个函数，堵住「认领一条 PR 时把旧 wakeOn 连同旧值写回」的路径。

## D-020 接不住的事实只记账，不排队

**2026-11-28。** 账号范围内的条目搜索（`author:@me` 等五条）会扫到所有能读的仓库，而投递只可能发生在本机「有会话在那里干活」或「有人订阅」的仓库里。两者不匹配时，事实照样入队，于是永远 pending：一台不干那件事的机器，每收到一次回复就攒一条送不出去的通知。实测：一台机器四天积了 41 条，日志每轮都在说 `30 in a repository nobody here works in`，面板上那行提醒跟着一直消不掉，而真正在做那个项目的另一台机器与此无关——通知是每台机器各自去取、各自清，跨机没有协议。

判据：`foldMineEvents` 把搜索命中的事实按仓库折叠，**只有本机能接住的仓库产生待办**；接不住的那些仍然推进 bookmark（`seen` 与 `lastMinePoll` 照写），所以将来真有人在那里开工时，历史是历史，不会一次倒出来，而轮询会留一行 `items: N change(s) … recorded, not queued` 说明忽略了多少。

替代的选项与它们为什么不够：

- **留着等认领**：认领是人的动作，一台根本不参与那个项目的机器上没人会去认领；这条路径只把积压变成常态。
- **只把搜索限定到已订阅仓库**：等价于把「有没有接收方」的判断藏进查询串里，日志就再也说不清被丢掉的是什么。折叠时拒绝并计数，判断留在代码里、留在日志里。
- **给事件加过期时间**：治的是症状，还得决定过期多久；而且「四天后忽然开始有人干这个仓库」时，意图应当是历史归历史，不是补发。

## D-021 清掉读过的线程不靠浏览器

**2026-11-28。** 在此之前，「清掉读过的」被拆成两层：条目级标已读走 API，仓库级（CI、安全告警、发布）靠 `scripts/clear-inbox.mjs` 起一个自带 profile 的浏览器、用 DevTools 协议点网页上的 Done。代价是三样：一个 584 行的 CDP 客户端、一份要登录的浏览器配置、以及一块面板上的「打开登录窗口」按钮——用户要用一个**没有他的书签和已保存密码**的陌生窗口收一次验证码。实测里它还经常空转：`clear-inbox: the browser never opened http://127.0.0.1:9333`，错误只落进日志。

根因是当初的判断「GitHub 的 Done 只有网页端点」。这一条今天仍然成立（`POST /notifications/beta/archive` 要网页会话 + CSRF，GraphQL 的 `Mutation` 上没有 `markNotificationThreadAsDone`），但**插件不需要 Done**：它要的是「这条别再报给我」，而 `PATCH /notifications/threads/<id>` 就够——已读的线程同样不在 `/notifications` 的未读流里。拿一个网页状态的名字去要求一个轮询器，才是不必要的耦合。

判据：删掉 `scripts/clear-inbox.mjs` 与整套 sign-in（`openSignIn`/`checkSignIn`/`signInLaunch`/`spawnSignIn`/`signInCooldownMs`/`sweep`/浏览器 profile/面板登录行）。清理由 `pollOnce` 里的 `markThreadsRead` 完成，和读收件箱同一条 `gh` 调用。新增一项 `doctor` 检查：令牌有没有 `notifications` 权限——缺了 PATCH 会回 404 并附带 `This API operation needs the "notifications" scope`，看起来像插件坏了，所以必须由 doctor 直说补法（`gh auth refresh -h github.com -s notifications`）。

替代的选项与它们为什么不够：

- **保留 Done，只把窗口做得不陌生**：还是要在空 profile 里输一次密码，只是少了点意外。棱角磨平了，耦合还在。
- **复制用户的浏览器 cookie 进专用 profile**：能免掉登录，但 Chromium 的应用绑定加密会让它静默失效，而且这是复制凭据——把一次登录换成一条不可预测的失败路径。
- **接管用户正在运行的浏览器**：DevTools 只能挂在启动时带调试参数的实例上；对已在运行的浏览器传端口，只会被转发成一个新标签页然后退出，这正是「窗口起不来」的来源。

## D-022 状态根属于插件，不属于工作区

**2026-11-28。** 状态一直写在 `<cwd>/.work/inbox-bridge` 与 `<cwd>/.work/github-inbox`。这条规则把「插件能不能工作」绑在了「用户的项目目录能不能写」上，而那个目录常常不能：只读或同步中的项目、别的账号建的目录、被 Defender 受控文件夹访问盯上的桌面、目标已消失的 Junction。表现是 `could not write … EPERM: operation not permitted, mkdir`，装的人从插件内部没有任何办法自救——连「在本机接管一个仓库」都会失败，因为那条路径要写 `prefs.json`。本轮实测到的就是这一例：另一台机器上接管仓库直接报上述 EPERM，而它装的版本、登录、仓库权限都没问题。

判据：新增 `scripts/state-root.mjs` 拥有「状态放哪」这一个问题，顺序是 `INBOX_STATE_ROOT`（相对路径按 `cwd` 解析）→ `$DSH_HOME`（默认 `~/.dsh`）→ `<cwd>/.work`，**第一个真正能创建、能写入的胜出**。探针是「建目录 + 写一个临时文件」，不是查权限位：能做的才是能用。插件把选中的根通过 `INBOX_STATE_ROOT` 传给抓取器与 ack 子进程；`runtime.json` 记 `state.root`/`state.from`；一次都没写成功时 `doctor` 的 `state` 项是 fail 并给出原因，面板也有一行。第一次用新根时，旧根的 `state.json`、`prefs.json`、`labels.json` 与抓取器状态复制过去（日志不搬，日志记的是它自己那次运行）。

替代的选项与它们为什么不够：

- **只加 `INBOX_STATE_ROOT`，默认仍是 `<cwd>/.work`**：装的人不设环境变量，就还是那个坏掉的默认值。默认必须是能用的那个。
- **探测失败后继续用 <cwd>/.work 并提示用户去修权限**：把一个插件能自己解决的问题，变成用户要跑的 `icacls`。修权限也不是人人能做（管理员、别的账号、托管盘）。
- **把状态放进 `<cwd>/.work` 但写失败时只存内存**：设置会静默消失，比报错更坏——用户以为接管成功了，重载后没了。
- **留在 `.work` 并靠文档提醒「别把这个目录当临时文件删掉」**：上一轮就是这么丢的——一次例行清理把 `.work/browser-profile` 连同 GitHub 登录一起删了。要求人记住某条路径不能删，是把机制问题写成注意事项。
